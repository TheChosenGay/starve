## 1. 项目概述

starve 是一个饥荒（Don't Starve）类生存游戏的服务器。架构分层与设计文档一致：

```text
Gateway(连接/协议)        Cluster(跨节点寻址/RPC)
        \                    /
         \                  /
          Actor(并发与所有权边界)
                   |
                ECS(模拟内核)
```

- 一个世界（房间）= 一个 world actor + 一个 ECS World；
- 客户端只连 Gateway（pomelo 协议），Gateway 通过 Actor 寻址投递消息，不直接碰 ECS；
- 单机 MVP 网关与世界同 engine（本地 PID 直连），跨节点是 M6（Cluster）阶段的事。

## 2. 已锁定的技术基线（摘自设计文档 §2/§7）

| 层 | 选择 |
|----|------|
| Actor 内核 | hollywood 风格：ringbuffer 邮箱 + 按需 goroutine + 批处理、类型化消息、崩溃缓冲 + 重启、PID 寻址、kind 激活 |
| ECS | 自研：稀疏集 + 泛型查询 + 惰性注册表（§4.3 原理） |
| 客户端协议 | pomelo（握手/心跳/route/request/notify/response/push），实现蓝本 = cherry `net/parser/pomelo` |
| 服务器间通信 | hollywood remote/cluster（dRPC，类型化 protobuf），**不走 pomelo** |
| Gateway | 自研：pomelo parser + agent/session + 路由注册表 |
| 确定性 | L1 固定系统顺序 + L2 种子化随机；**不做 L3 lockstep** |

关键纪律（所有里程碑必须遵守）：

1. ECS 系统是纯函数：不调 actor API、不发网络消息，副作用只走 outbox；
2. 随机数一律从 `world.Resource[RNG]` 取，禁止全局 `rand` 与系统内 `time.Now()`；
3. tick 内禁止同步跨 actor 调用；world actor 执行超时默认 300ms（可配置）；
4. 路由与消息类型契约定义在共享 protobuf，客户端/服务端复用同一套 proto。

#### M5 收尾：离线保护 + 指令日志

- **离线保护**：网关轮询 ConnManager 检测断线（combet 无 OnClose 回调）→ 通知世界挂 `Offline{SinceTick}`；
  重连同 UID 且未死亡复用实体（清标记原地续玩）；超时（`GATE_OFFLINE_SECONDS`，默认 300s）销毁并广播移除；
- **指令日志**：世界记录 `JournalEntry{Tick, UID, Seq, Kind, Data}`（命令 + 登录/断线/销毁事件，JSON），
  随存档保存在 `SaveData.journal`；`WorldActor.Replay` 按日志从空世界确定性重放，
  验收 = 重放后 `FullSnapshot` 与同 tick 存档快照逐字节一致（`TestReplayMatchesSnapshot`）。

#### M5-C 采集（方案 A：资源计数，已定）

- 组件：`Gatherable{Kind, Count}`（可采集目标）+ `Inventory{Resources map[ResourceKind]int32}`（玩家资源计数）；
- 资源类型：proto 枚举 `ResourceKind`（稳定 ID，wire 上是 int32）；配置表仍写字符串，加载时解析校验（未知 kind 报错 fail fast）；
- 采集流程：`world.player.gather` 路由 → 命令直接执行（校验所有权/距离/未耗尽）→ 目标 Count--、玩家资源++；
- 耗尽：`Remove[Gatherable]`（实体保留，组件消失）；增量快照新增 `RemovedComponents` 字段通知客户端组件被移除；
- **资源配置表**：`configs/resources.json` 定义种子实体（Kind/坐标/Count），启动时 seed，加资源零代码；
- **资源模板表（M5 二期）**：样式/颜色/掉落/重生等静态属性用 `kind → Template` 模板表（服务端数值表 + 客户端美术/prefab 表），不塞进枚举；枚举只承载身份，扩展面在模板表；
- **完整背包系统（掉落/拾取/使用/制作）作为 M5 二期独立里程碑**，服务端估 5~8 人日，不混入当前闭环。

#### 配置 vs 代码的分层原则（已定）

- **数值/内容**（速率、伤害、实体位置、物品定义）→ 配置表，不改代码；
- **身份/机制**（资源类型枚举、新命令、新系统）→ 代码 + proto；资源枚举每加一种就改一次 proto，但静态属性走模板表，游戏逻辑不动；
- **组件组合**（复用现有机制加资源类型）→ 近乎零代码（ECS 横切组合）；
- **机制/行为**（新命令、新系统）→ 必须写系统/命令代码。

## 7. 玩法系统编写规范（dt 与 System）

给所有（含 AI 编写的）玩法系统定的规矩，M5 起强制执行。

### dt：固定步长，由 actor 注入

- 时间一律由 actor 在每个 tick 注入（M3 起 10Hz → 100ms），系统内**禁止** `time.Now()` 与全局 `rand`（设计文档 §5.2 纪律 3）。
- dt 实际是常量，系统可以只按"每 tick 一次"写；dt 参数的意义是显式化"时间在流动"，将来做暂停 / 慢放 / 回放快进时不用改接口。
- 世界时钟 = tickCount × dt，存档恢复时从存档读取，不重新计时。

### System 的实例化形态

- **一个系统一个 struct**：零字段或少量配置字段，注册一次、长驻复用，不是每 tick 新建：

```go
type HungerSystem struct{ Rate int } // 配置字段，创建时定好

func (s *HungerSystem) Update(w *ecs.World, dt time.Duration) {
    ecs.Query[Hunger](w, func(e ecs.Entity, h *Hunger) {
        h.Level -= s.Rate // 固定 dt 下可只按 tick 计
    })
}

w.AddSystem(OrderSim, &HungerSystem{Rate: 2})
```

- **系统尽量无状态**（只留配置字段）：需要跨 tick 的状态放组件或 Resource，不放系统字段——系统实例是共享单例，字段会变成隐式全局状态，破坏确定性。
- **order 按阶段常量填**：阶段常量在 `internal/game` 统一定义（如 10=输入 / 100=模拟 / 1000=结算），玩法代码里不散落魔法数字；约定见 §4 M1 `AddSystem` 注释。
- 系统是纯函数：不调 actor API、不发网络消息，副作用只走 outbox（M3 接缝）。

## 8. 性能基线（M2 完成时）

> 环境：Apple M4 Pro（GOMAXPROCS=12），Go 1.25.3，`-benchmem`，默认 `-benchtime=1s`。
> 代码：`actor/bench_test.go`（actor 模块）+ `internal/ecs/sparse_set_bench_test.go`（ECS），`make bench` 一键跑。

### 8.1 CPU 数扫描（ns/op，越小越快）

| 基准 | 1 核 | 2 | 4 | 8 | 12 |
|---|---|---|---|---|---|
| 邮箱 push+pop | 65.0 | 63.5 | 63.6 | 63.3 | 63.7 |
| Send（单发送者→actor，端到端） | **77.0** | 94.5 | 106 | 104 | 105 |
| Send 并发（多发送者→单 actor） | **72.3** | 83.1 | 123 | 144 | 151 |
| actor→actor 两跳 | **160** | 186 | 235 | 232 | 232 |
| Request/Respond 往返 | **1114** | 1331 | 1451 | 1440 | 1452 |

结论：**单 actor 的吞吐受"单消费者"限制**，加核数反而因邮箱争抢变慢。
单 actor 天花板约 1300 万 msg/s（77ns）；水平扩展靠多 actor / 多世界（§6 与设计文档"世界边界"结论一致）。

### 8.2 时长稳定性（1s vs 3s）

| 基准 | 1s | 3s |
|---|---|---|
| EngineSend @1核 | 77.0 | 76.7 |
| EngineSend @12核 | 105 | 103.5 |
| RequestResponse @1核 | 1114 | 1082 |
| RequestResponse @12核 | 1452 | 1430 |

数字稳定，差异在噪声范围。

### 8.3 内存占用

| 基准 | B/op | allocs/op |
|---|---|---|
| EngineSend | 45–49 | 1 |
| Send 并发 | 33–37 | **0** |
| actor→actor | 91–133 | 2 |
| Request/Respond | **10,312** | 9–10 |
| Spawn（默认邮箱 1024） | **33,415** | 9 |
| Spawn（邮箱 64） | **2,932** | 9 |

要点：

- **actor 稳态内存大头是邮箱缓冲**：`MailboxSize × 32B`（envelope 大小）。默认 1024 ≈ 32KB/actor；调到 64 ≈ 2.9KB/actor，差一个数量级。
- 规模换算：默认邮箱下 100/1000/10000 个 actor ≈ 3.3MB / 33MB / 334MB；邮箱 64 下 ≈ 0.3MB / 2.9MB / 29MB。
- 用法：agent/world 这类数量少、峰值流量高的 actor 用大邮箱；actor 数量大时调小 `MailboxSize` 是免费省内存手段。
- Request/Respond 每次 10KB（定时器 + 通道 + 信封），低频查询没问题；若变热路径，上对象池/定时器复用（设计文档 §3.2"消息池 MVP 不做，等 profiling 有数据再上"——基线已就位）。

### 8.4 ECS 对照（M1 完成时）

| 基准 | 结果 |
|---|---|
| 稀疏集 Add | ≈ 5.3ns，0 alloc |
| 稀疏集 Get | ≈ 1.3ns，0 alloc |
| 1 万实体全量 Query | ≈ 7.6µs/op，0 alloc |

ECS 内核开销在 10Hz tick 下可忽略；本表作为 M3 接缝与 M5 玩法系统上线后的对比基准。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| actor 内核自研复杂度高 | M2 延期 | MVP 裁剪：不做消息池/零分配，批处理默认值先用 300 |
| pomelo SDK 兼容（dict/protos 压缩） | M4 协议对接延期 | MVP 用标准 protobuf 编码，dict 压缩二期移植 cherry 实现 |
| 玩法迭代破坏确定性 | M5 回放/存档回归 | L1/L2 纪律写入测试，确定性测试作为 CI 门禁 |
| Cluster 复杂度蔓延 | M6 范围失控 | 单机 MVP 明确不引入跨节点；M6 前不做跨节点设计实现 |

## 10. 决策记录

所有技术决策见《游戏服务器设计-Actor与ECS.md》§7「已定决策汇总」；本方案只负责把它们落成分期计划与任务清单。后续新增决策（如 module 路径、存档格式、玩法范围）在此文档追加。

- 2026-08-04：**Gateway 复用评估**——不整体依赖 `~/feeds` 的 comet（自定义帧协议与 pomelo 不兼容，且 import 会拖入整模块依赖）；以其连接层骨架（单写者写泵 / ConnManager / 协议无关 Core）为 `internal/gateway` 实现蓝本。详见 [gateway-comet复用评估.md](gateway-comet复用评估.md)。
- 2026-08-04：**Go 泛型 API 形态**——Go 不支持泛型方法，设计草案 §4.5 的 `w.Add[T]` / `w.Query[T]` 以包级泛型函数实现（`ecs.Add[T](w, e, c)`、`ecs.Get[T](w, e)`、`ecs.Query[T](w, fn)`、`ecs.Query2[A, B](w, fn)`），类型安全不变，仅调用形态变化。
- 2026-08-07：**存档回归 actor 线性模型**——`Save()` 只在世界 actor goroutine 上执行（SaveRequest / onTick 内），外部经 actor 消息触发，不加锁（删除了临时引入的快照锁与原子 tick）；客户端存档走 `game.save` 路由，事件触发走 `SaveNow()`（预留）。
- 2026-08-07：**采集方案 A + 配置驱动**——采集用 `Gatherable` + `Inventory` 资源计数（完整背包系统 M5 二期）；资源种子实体由 `configs/resources.json` 配置驱动（数值/内容配置化、机制代码化、ECS 组合复用）。
- 2026-08-07：**资源类型枚举化**——`Gatherable.Kind`/`Inventory` 键用 proto 枚举 `ResourceKind`（稳定 ID）；配置字符串加载时解析，未知 kind fail fast；样式/颜色/掉落等静态属性后续走 `kind → Template` 模板表，不在枚举里堆属性。注：proto3 的 map 键不允许枚举，`Inventory.resources` 用 `repeated ResourceCount{kind,count}` 表达（语义等价，codec 排序保证确定性）。
- 2026-08-07：**M5 收尾——离线保护 + 指令日志**——断线保留 N 分钟（重连复用实体，超时销毁）；`JournalEntry` 指令日志随存档保存，`Replay()` 从空世界确定性重放并与存档快照互验（input journal 思路，存档存"世界状态"、日志存"操作序列"）。
- 2026-08-08：**M5 二期 A 设计**——掉落统一挂 Dead（植物/石头/生物效果由模板差异化）；背包升级 `ItemStack{kind,count,max_stack}`（proto 字段号兼容旧档，不迁移）；`use_effect`/`drop_table` 都在资源模板表；制作（crafting）独立二期 B。
- 2026-08-08：**WorkSystem 落地**——环境物 `Workable{Action, WorkLeft}` 取代 Gatherable/Health；工具 `tool{action,efficiency,durability}` + `Equipped` 动态解析（属性在模板、耐久在物品实例）；chop/mine/equip 命令；命令处理独立 CommandHandler（world actor 只管世界）。
- 2026-08-13：**重连语义——一律复用实体 id，不复活不恢复状态**——同 UID 重连只清 Offline 标记并返回同一实体（含已死亡实体）；死亡角色重连显示为尸体，不再原地复活/回满血，也不新建实体（避免"分身"）。死亡→重生流程由后续机制单独设计。
- 2026-09-08：**碰撞检测架构——服务端权威 + 客户端表现，不共享碰撞代码**——命中/伤害/AOI 过滤只由 Go 服务端 `pkg/collide` 判定（权威）；C# 客户端只做移动预测与表现反馈（P1.1/M6 已定"攻击只预测动画/进度，不预测权威结果"），不引入碰撞库、不复制 Go 数学。实现选型：纯 Go 窄阶段（胶囊-胶囊、线段/射线-胶囊、盒-胶囊、球-盒）自实现（依据 Ericson《Real-Time Collision Detection》第 4/5 章），宽阶段用 `github.com/tidwall/rtree`（3D AABB，MIT，无 cgo）；明确**不用 cgo 物理引擎**（Jolt/Bullet/PhysX 会破坏跨编译与确定性）。一致性只在两端都计算的输出（移动步进/坡度因子）上要求，沿用 `testdata/movement_golden.json` 金标准向量；碰撞派生结果为服务端独有，无需与客户端一致。数值/规则参数（半径、射程、角度、伤害、冷却、弹速）统一走服务端配置/协议，不复制到客户端。
- 2026-09-14：**阻挡语义重定义：占位 ≠ 不可走**——整格阻挡会让角色离树整整一格外停下（树只占格心一小块）。改为三层：**地形**（水/悬崖不可走）、**占位**（`Block`：`radius>0` 格心圆=树/岩，`radius=0` 占格盒=建筑/工作站；占位格仍可走，只加寻路代价——圆 6 / 盒 1000——并作为放置冲突依据，一格只归一个占位物）、**形状**（移动时连续扫掠 + 沿接触切面滑动，完全被挡时墙角兜底沿较近轴推出）。移动的"碰撞 + 侧滑 + 格子提交"抽成独立函数 `systems.MoveBody`，`MoveSystem` 只管速度。移动体半径 `systems.BodyRadius=0.305` 与占位形状同属 P1.1 契约，两端必须一致（客户端指南见《占位物与墙角滑动-Godot客户端适配指南》）。
- 2026-09-14：**实体碰撞体 = 模型胶囊 + 调试可视化**——服务端每个实体的碰撞体是客户端模型的胶囊（`capsule`：`axis`/`a,b`/`radius`/`height`），长宽高按规则刚好包住模型：半径取取样带短边一半（树干/躯干，四肢不进半径）、四足的段沿水平长轴铺开（鼻子尾巴都包住）、高度取整个模型跨度。`Moveable` 增加 `body_radius/body_height/body_half_length/facing`，移动走 `collision.World.SlideBody`（圆柱或胶囊扫掠，`pkg/collide.SweepSlideCapsule` 用"沿轴采样球"复用球×形状内核 + 宽阶段剔除）；缺省半径 `systems.BodyRadius` 从写死的 0.2 改成玩家模型推导值 0.305。调试：`GATE_DEBUG_COLLISION=1` 时 `DebugShapeSystem` 给每个实体挂 `DebugShape` 随快照下发，客户端 `DebugShapeLayer3D` 画半透明体核对"是不是刚好包住"。客户端本地预测改用服务端下发的 `Moveable.body_radius`（`OwnMovementSim.SetBodyRadius`）。
- 2026-09-14：**模型 → 服务端简化碰撞体流水线**——服务端每个实体的碰撞体必须来自客户端模型，不能手填（手填数值会随美术改模型失真且没人发现）。新增 `pkg/modelcollide`（纯 Go 读 `.glb`：节点变换 + 蒙皮绑定姿势）与 `cmd/modelcollide`：按 `configs/models.json` 清单（模型路径、客户端缩放常量出处、取样高度带、分位、落点字段）推导出简化碰撞体，生成 `configs/model_collision.json`；简化规则是"高度带内水平截面的**短边一半**"（长条模型不含体长）+ 分位裁离群点 + 建筑足迹向上取整。`make check` 里的 `config-check` 会校验游戏配置（模板 `collision_radius` / 建筑 `width,height` / 生物 `body_radius,body_height`）与流水线一致，不一致直接报错并给出目标值；`make model-collide` 重新生成，`make model-collide-verify` 抓"改了模型忘了跑流水线"。详见[模型到碰撞体流水线](模型到碰撞体流水线.md)。
- 2026-09-14：**终端客户端 `cmd/tui`**——开发期不想/不便开 Godot 时的轻量客户端：启动 < 0.2s、终端里跑、不需要图形环境，同时天然 CI 友好（`-dump` 不需要 TTY，连上网关收一帧就退出）。协议完全复用 `tools/pomelo-client` 那一套（握手/登录/`world.player.*` notify），世界状态单线程、网络与按键都从 channel 进主循环。渲染是**俯视格视图**而不是等距——因为这个 TUI 的定位是验证服务端语义：地形/实体/以及 `c` 键的**碰撞体叠加层**（圆按格心、盒按足迹、`GATE_DEBUG_COLLISION=1` 时优先用下发的 `DebugShape`），能直接肉眼核对"占位 ≠ 不可走"是否成立。宽字符（中文）按两列计算，否则 HUD 会把布局挤歪。用法与按键见[终端客户端-TUI](终端客户端-TUI.md)。
- 2026-09-14：**DebugShape 空间契约收紧（修 3 个"碰撞体对不上渲染模型"的 bug）**。症状是客户端调试层里有些形状与模型不重叠、有些朝向不对。根因不在物理（服务端真实碰撞与渲染是自洽的），而在调试形状的空间契约没写清、两端各做了一半变换：① 盒被偏移两次——实体节点已由 `BlockVisual.Center` 摆在占格中心，客户端又按"锚点在左上角"叠加 `(w/2,h/2,d/2)`（1×1 差对角半格、2×2 火堆差 2 格）；② 移动体胶囊 `a_y/b_y=0`——胶囊以节点原点为中心，玩家半截埋地、四足躺在脚底；③ 胶囊轴发了**世界朝向**而客户端又按朝向转一次，方向误差恰好等于朝向角（+Y 看着对、对角差 45°、+X 差 90°）。修法：把契约统一成**实体节点局部空间**——服务端只发模型局部 +Z 的段（直立取 `[r, 身高-r]`、四足取身高中心）与以节点为中心的盒，客户端只跟随节点、不重复施加变换；`game.proto` / `components.DebugShape` / P1.1 / 客户端指南同步写明。回归锁：`TestDebugCollisionCapsuleAxisStaysModelLocal` 用 **+X 朝向**断言段仍沿局部 Z（旧的 `+Y` 朝向对 bug 免疫，正是它漏掉的原因）、且换朝向后形状完全不变。
- 2026-09-14：**寻路/避障改动 CR 结论——设计合理，遗留项已登记**。判为"偏优秀"：三层语义（地形/占位代价/形状）分工干净、`Walkable` 退回只看地形反而让客户端**删掉了动态阻挡层**、移动内核的四条语义细节（连续扫掠 / `skin` 回退 / 初始重叠推出 / 墙角兜底）齐备、金标准向量跨语言共享且客户端确实在消费新字段（`shapes`/`body_radius`/`tol`，两侧 `movement_golden.json` 字节相同）、模型→碰撞体流水线做到了"配置由资产推导 + `make check` 门禁 + `-verify` 抓漏跑"。门禁全绿（`build`/`test`/`vet`/`gofmt`/`proto-check`/`configcheck`/`modelcollide -check`）。**当时判为"未达优秀"的原因（P1 追击不可达的每 tick 全图 A\*、P2 寻路不含体积、P3 `popPathStep` 跨轴耦合、P4 金标准容差偏松、P5 小项、提交卫生）见 §11「寻路与避障」——其中 P1 已在本日随后修复（见下条），其余仍在待办**。
- 2026-09-14：**寻路 P1 修复——不可达判定不再需要搜索**。`AISystem.chase` 在目标不可达时每 tick 重算一次 A\*，而未命中目标意味着 A\* 必须展开完整个连通分量。修法：`MapData` 增加**地形连通分量惰性索引**（`Reachable`：四邻接洪水填充，O(W×H) 建一次、之后 O(1)；`InvalidateReachability` 显式失效，`attachMap` 调用），`FindPath` 开搜前先快查——**分量 id 不同 ⇔ 一定无路**，于是"不可达"从毫秒级搜索变成常数判定。索引不受占位物增删影响（占位格仍可走），所以砍树/拆建筑都不失效。实测 256×256 隔河追击 200 只狼：**958 ms/tick → 0.223 ms/tick（4300×）**，分配 **868 MB → 28.8 KB**。回归锁见 §11。

- **寻路与避障（2026-09-14 三层阻挡落地后的遗留项，按优先级）**：
  - **[已修复] P1 生物追击不可达时每 tick 做一次全图 A\***（`systems.AISystem.chase`：`FindPath` 返回空 → `Path` 保持空 → 下一 tick 再算）。修法不是"把昂贵搜索摊薄"，而是**让不可达判定不再需要搜索**：`MapData` 增加地形连通分量惰性索引（`Reachable`，四邻接洪水填充，O(W×H) 建一次、之后 O(1)），`FindPath` 开搜前先做快查——分量 id 不同 ⇔ 一定无路。索引不吃占位物变更（占位格仍可走，所以砍树/拆建筑都不失效），只有换地图/读档需要 `InvalidateReachability`（`attachMap` 已调用）。实测（256×256、200 只狼隔河追 100 个玩家、AOI+AI 一 tick）：**958 ms → 0.223 ms（约 4300×）**，分配 **868 MB → 28.8 KB**；`worldmap` 侧不可达查找 **6.88 ms（128×128）→ 5.1 ns 且与地图规模无关、0 分配**。回归锁：`worldmap.TestFindPathUnreachableSkipsSearch`（断言 A\* 展开数为 0）、`world.TestAIUnreachableChaseKeepsSemantics`（AI 对外行为不变）；基准 `BenchmarkFindPathUnreachable` / `BenchmarkAIUnreachableChase`。
  - **P2 寻路不含体积，"代价 6 / 1000" 是手调常数**。A\* 只按格心连通性搜，不知道 `BodyRadius`。同一格宽走廊里：`wood`(r=0.103) `0.103+0.305=0.408 < 0.5` **能过**，`flint`(r=0.28) `0.585 > 0.5` **过不去**，但两者在 A\* 眼里都是"代价 6"。于是 A\* 会给出身体过不去的路径，而 `MoveBody` 只在原地滑、不报告失败 → **失败模式从"判不可达"变成"静默卡死"**（玩家自动行走路径截到 `maxWalkPath=32` 且不重算；生物重算得到同一条死路，循环卡住）。**修法**：先加"进度看门狗"（连续 N tick 位移 < ε 且路径未推进 → 丢路径重算或退避）；中期把代价从体型推导（clearance / 膨胀图），并考虑 string-pulling 把 4 向阶梯路径拉直。
  - **P3 `popPathStep` 的跨轴耦合**（`systems.MoveBody`）：X/Y 两个分支各自在跨格时弹队首，而 `dir` 是意图方向；形状层可能返回非零的垂直分量（贴盒角滑动的法向投影），此时垂直轴的跨格会**多弹一个路径点**——走廊路径是连续同向步，一步位移会吃掉两个路径点。已用 `MoveBody(dir=(1,0), stepX=stepY=0.5, path=(1,0)×3)` 复现 `path 3 → 1`；但另外用 196 组（`subY` 全遍历 × 阻挡盒 4 个 y 位置）扫描**未能构造出真实触发场景**（角区推出总是背离障碍，且障碍角点在整数格边界，`sub` 落不到能跨格的区间），故定为**潜在缺陷**。**修法**：只在跨格轴与路径步方向对应时才弹（3 行），并补一条回归测试。
  - **P4 金标准容差偏松 + 只有单 tick 向量**：带接触的向量 `tol=2e-3`，而 `skin=1e-3` —— 客户端即使漏掉 skin 回退也可能通过；服务端 `float64` / 客户端 `float`（`MovementSlide.cs`）在这个量级的差异实际只有 ~1e-6。且每条向量只推进一步（`sim.Tick(DTMS)` 一次），单 tick 误差掩盖不了、但多 tick 贴墙滑行的累积误差没有契约覆盖（而"贴近树/墙来回校正"正是这套契约要解决的问题）。**修法**：容差收到 `2e-4` 级别试跑两端；补"贴墙滑行 20 tick""绕树 12 tick"这类多 tick 向量（两端 `MovementGoldenTests` 的逻辑已支持，只需加数据）。
  - **P5 小项**：① `MapData.Occupied` 同时充当放置互斥矩阵与寻路代价，`SetOccupied(0)` 是**覆盖清零而非引用计数**——两个占位物压同一格时先注销的会把格子清空（当前 mapgen 用 `min_dist` 保证不重叠，风险低；建议加重叠断言或改计数层）；② `systems.stepAxis` 的 `sub ∈ [0,1)` 不变式在 `sub + dist ≥ 2` 时破坏且只校验 1 格可走性（当前最大 `dist`：tile 效果 +100% → `speed 20 × 50ms = 1.0`，安全），建议加 `clamp` 或断言做纵深防御；③ `worldmap.FleeDir` 候选表含指向威胁的方向（`{-dx,dy}`/`{-dx,-dy}`）且不考虑 `IsOccupied`，与 `walkTo`/`haunt` 的做法不一致；④ `ecs.TryResourceOf` 遍历 map 返回"第一个实现接口的资源"，顺序不确定，建议加"只能有一个 `BlockerTarget`"断言；⑤ `config/templates.go` 的 `collision_radius < 0.5` 校验只在配置加载层，`components.Block.Radius` 本身无约束（它是"一格一圆"成立的前提，值得注释标明）。
