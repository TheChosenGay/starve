# P1.3 输入流：序号消费与多步追赶

## 目标

把"客户端发来的操作"变成服务端可复现的**操作流**：**每条操作都必须恰好被消费一次、配一步（或零步）位移**，
从而让客户端能拿"执行完第 N 条之后我自己的状态"和"服务端第 N 条之后的权威状态"**直接比较**。

配套的客户端侧语义见 `starve-godot/P1.7-序号锚定-命令流-追赶-渲染.md`；
更早的协议契约见 `P1.1-移动预测协议契约.md`。

---

## 1. 数据流

```
命令到达（ws） → 按 player 入队（ControlQueue.Pending，按 seq 插入 + 去重）
   ↓ 每个世界 tick（GATE_TICK_MS=50，20Hz）
consumeOps()   → 从 consumed+1 起**连续**消费；每条 move 记一个"逐步方向"（Steps）
   ↓
MoveSystem     → 跑 max(1, K) 轮：每轮用那条操作自己的方向走一步（K 条 = K 步）
   ↓ 系统跑完
commitConsumedInputs() → 推进 last_accepted_seq（= 本 tick 真正消费掉的 seq）
   ↓
投影/快照      → 位置（已烘进 last_accepted_seq）+ tick + input_epoch + last_accepted_seq 同一条消息
```

---

## 2. 队列语义（`internal/game/systems/control_system.go`）

| 字段 | 含义 |
| --- | --- |
| `Pending` | 每 Actor 未消费的操作（move/attack/cancel **共用一条队列**，按 seq 插入排序） |
| `Steps` | 本 tick 消费掉的 move 的**逐步方向**（MoveSystem 按它跑子步） |
| `Consumed` | 本 tick 真正消费掉的操作（供 ACK 推进） |
| `OpDriven` | "由客户端操作流驱动"的 Actor（收到过带 seq 的操作） |
| `StepBudget` | 单 Actor 单 tick 最多走几步（0 = `StepBudgetDefault = 3`） |
| `MaxPending` | 单 Actor 队列上限（0 = `MaxPendingDefault = 8`），超出丢**最旧**并 `Dropped++` |

**为什么共用一条队列**：客户端所有操作共用一个自增 seq，序号顺序就是玩家的操作顺序。分开排队会让
`move(5)` 被 `attack(6)` 插队 —— 顺序反了，"第 N 条之后的状态"两边就对不上。

**为什么按 seq 插入而不是"最后一条赢"**：网络抖动必然把几条操作挤进同一个服务端 tick；只留最后一条
⇒ 被丢的那几条在服务端**永远不生效** ⇒ 和解必然出现假失配。排队 + 按序消费（积压时追赶）才是
"在服务端复现客户端操作流"。

**去重**：客户端每帧都在重发未确认窗口（`ack+1` + 最新几条），所以同一个 seq 会重复到达 —— `hasSeq`
直接忽略队列里已有的那条。

## 3. 多步追赶（K 条 move = K 步）

一次 tick 允许消费 **K 条**（K ≤ `StepBudget`），且**每条配一步移动积分**，每步用**那条操作自己的方向**。

* 为什么需要：客户端每 tick 采样一条，但网络抖动会把几条挤进同一个服务端 tick。若一个 tick 只消费一条，
  队列会变成随机游走（进 1 出 1，突发后永远回不到 0），玩家的操作会被**永久**推迟。
* `MoveSystem.Update` 先算 `rounds = max(1, max(len(steps[e])))`，然后跑 `rounds` 轮子步；
  `participatesInRound` 保证每个实体只跑到自己步数用完为止（所有追赶中的实体一起做"先全部求解、再按 id 提交"，
  保持顺序无关性）。
* 每条 move 恰好一步，所以**不会出现"消费了但没走"** —— 否则"第 N 条之后的状态"在两边就不是同一个东西了。
* Action/Cancel 不占移动步（它们不产生位移），但**照样按 seq 消费并推进 ACK**。

单 tick 步数上限同时是防加速闸门：一帧最多 K × 50ms 的移动。

---

## 4. "没操作就不许走"（`OpDriven`）

**规则**：收到过带 seq 操作的 Actor，每 tick 都在 `Steps` 里占一个条目；**这一 tick 没消费到操作时是空条目**。
于是 `participatesInRound` 对它返回 false，MoveSystem **不会替它跑保留意图的第 0 轮**；同时把这些 Actor 的
`VelX/VelY` 归零（否则别的客户端会拿上一 tick 的速度继续外推）。

**为什么必须这样**：MoveSystem 对"没有逐步方向表"的实体默认按 `effectiveDir(mv)`（Path 队首或上次输入方向）
走第 0 轮 —— 那是 **AI/生物**的语义。对操作驱动的玩家，这等于"包还在路上时服务端白走一步，而 ACK 不涨"：

> 服务端位置比"ACK 对应的状态"多走了一步 ⇒ 客户端每次锚定比较都差 0.5 格（正好一个 tick 的位移，转向处翻倍）
> ⇒ 每份快照都要校正一次 ⇒ 表现就是"走着走着时不时卡一下"。

**AI/生物不受影响**：它们不发带 seq 的操作，不进 `OpDriven`，仍然按 tick 自己走（第 0 轮）。

**代价**：输入真的迟到时，这个玩家会**冻结一个 tick**（而不是继续滑行）。这是正确的：客户端自己的预测
还在前面，操作到达后服务端会追步补上，玩家看不到停顿；而"继续滑行"会让两边状态永久错位。

---

## 5. 缺口与宽限

* 只从 `consumed+1` **连续**消费；不连续就等（乱序/丢包的补齐包还在路上）。
* 等超过 `maxGapWaitTicks = 3`（150ms）才跳过缺口，并 `Desyncs++`。
  * 为什么不是无限等：等待的代价是"缺口之后的输入全被卡住"，比丢一条操作更伤手感。
  * 为什么是 3：客户端的冗余窗口（4 条）覆盖 150ms 内的重发；TCP 传输下缺口基本只来自"客户端真的没发"。
* 跳过之后两边会差"那条操作的位移"，客户端下一次和解会 rebase + 按自己的节拍重放 ⇒ 自愈。

## 6. 世代（epoch）

`BeginInputEpoch` 分配非零 epoch；换世代时 `ResetActor` 清掉 `Pending / Steps / consumed / gapWait / OpDriven`。
同 UID 重连会拿到新 epoch、旧连接被踢 —— 避免"旧流的 seq"和"新流的 seq"接在一起。

## 7. 世界时钟保护

`dropOverdueTicks`：世界 tick 落后墙钟超过 `maxTickDebt = 4` 就丢 tick（`DroppedTicks++`），
避免过载后越追越远（追到的是"过去的现在"）。

## 8. 不变量（回归测试钉住的东西）

1. **K 条 move = K 步**，每步用自己那条的方向（`TestBunchedSequencedMovesCatchUpInOneTick`：+X 再 −X ⇒ 净位移 0）。
2. **操作驱动的玩家，本 tick 没操作就一步不走**，且速度归零；下一条到达后正好走一步（`TestIdleOpDrivenPlayerDoesNotCoast`，已做突变验证）。
3. **不是操作驱动的实体仍然按 tick 走**（`TestNonOpDrivenEntityStillMovesEveryTick`）。
4. 步数预算把追赶限速（`TestStepBudgetPacesTheMoveStream`）；每人一条独立流（`TestEachPlayerHasItsOwnMoveStream`）；重发/乱序去重（`TestRedundantAndOutOfOrderOpsAreDeduped`）。
5. **ACK ≡ 位置**：快照里的位置就是"执行完 `last_accepted_seq` 条操作之后"的状态（客户端和解的全部前提）。

跑法：`go test ./internal/game/world/ ./internal/game/systems/`（全量 `go test ./...`）。

## 9. 观测

服务端采样日志（`GATE_LOG_LEVEL=debug` 打开；默认 INFO 会被丢掉）：

| 字段 | 读法 |
| --- | --- |
| `cmd_backlog` / `cmd_max_backlog` | 当前/峰值待消费操作数。**持续 > 0** = 消费跟不上到达 |
| `catchup_steps` | 本 tick 因追步多跑的步数（> 1 步的部分） |
| `dropped_ops` | 因队列上限被丢的操作数（`MaxPending`） |
| `dropped_ticks` | 因世界时钟落后被丢的 tick 数（`maxTickDebt`） |
| `desyncs` | 跳过缺口的次数（每次跳过 = 服务端少走一条操作的位移，客户端会校正回来） |

判读：本机干净链路应当是 **`desyncs = 0`、`backlog = 0`、`catchup_steps = 0`、`dropped_* = 0`**；
一旦 `desyncs` 增长，先去客户端看"冗余窗口有没有把 `ack+1` 发出去"。

## 11. 硬规则：**移动相关组件必须每 tick 标脏**

> 这条规则踩过**两次**，且两次的现象完全不同，所以单独成节。

**规则**：任何表示"位置/位移"的组件（`Position`、`Moveable`、`Thrown`…），只要本 tick 动了，
**就必须标脏**；**绝不能**写成"只在跨格/整格坐标变化时标脏"。

**为什么**：快照只下发**脏组件**（`world_actor.go` 的 `DrainDirtySorted`）。一旦按"跨格"筛，
客户端拿到的样本密度就远低于 tick 率，而渲染是 60FPS、插值器只能外推极短一段就得到顶 ⇒ 冻结等下一格。

| # | 事故 | 写法 | 现象 | 修法与回归 |
| --- | --- | --- | --- | --- |
| 1 | `Moveable` 只在跨格时标脏 | `if crossed { MarkDirty }` | 10 格/秒 ÷ 20Hz = 0.5 格/tick ⇒ 每两 tick 才跨一格 ⇒ 客户端只有 **10Hz** 有效位置更新；实测 **61% 的渲染帧位置完全不变**，走动"一卡一跳" | `move_system.go` 改为 `if subMoved \|\| mvChanged { MarkDirty }`；`move_dirty_test.go` |
| 2 | `Thrown` 只在整格变化时标脏 `Position` | `if p.X != nx \|\| p.Y != ny { MarkDirty }` | 飞行约 0.29 格/tick（8 格飞 28 tick）⇒ 客户端 **2.5~3.5 tick** 才有一个样本、每次跳整 1 格 ⇒ **炸弹一格一顿**（实测 14 tick 只标脏 8 次） | `throw_system.go` 改为每 tick 都标脏；`throw_dirty_test.go` |

**落地要求**（新加移动类组件时照抄）：

1. 组件"动了"就 `ecs.MarkDirty[...]`，不要用"值变了才标"以外的筛子；整数化的组件尤其危险
   （整格 `Position` 承载浮点运动时必然出现"多 tick 值相同"）。
2. 加一条 `*_dirty_test.go`：跑 N 个 tick，断言该组件在 **N** 个 tick 里都被标脏
   （范式：`move_dirty_test.go`、`throw_dirty_test.go`）。
3. 精确的连续量（浮点位置/进度）尽量单独用一个组件承载并每 tick 下发，别硬塞进整格表示。
