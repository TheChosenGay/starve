# 模型 → 服务端简化碰撞体流水线

> 工具：`cmd/modelcollide`（纯 Go，无外部依赖，直接读客户端 `.glb`）  
> 清单：[`configs/models.json`](../configs/models.json)（手工维护）  
> 产物：[`configs/model_collision.json`](../configs/model_collision.json)（生成，提交进仓库）  
> 相关：[占位物与墙角滑动-Godot客户端适配指南](占位物与墙角滑动-Godot客户端适配指南.md)、[P1.1 移动预测契约](P1.1-移动预测协议契约.md)

## 1. 为什么要有这条流水线

客户端每个模型（树、岩石、人物、动物、建筑）在服务端都要有**简化碰撞体**：
角色能不能贴过去、寻路绕不绕、建筑占几格，全靠它。而简化碰撞体必须来自模型本身，
不能靠手填——手填的数值会随着美术改模型而失真，而且没人会发现。

所以流程是：

```
客户端 .glb  →（cmd/modelcollide 读顶点 → 按清单规则简化）→  服务端碰撞体（单位=格）
                                                              ├─ configs/model_collision.json（生成，进仓库）
                                                              └─ 落到游戏配置：模板 collision_radius / 建筑 width×height / 生物 body_radius+body_height
```

`make check` 里的 `config-check` 会跑 `-check`：**只要游戏配置和流水线推导不一致就报错**，
并把"该改成多少"打出来。也就是说模型是碰撞体的源头，配置只是它的落点。

## 2. 命令

```bash
go run ./cmd/modelcollide                 # 只读：打印推导结果 + 验收 + 漏登记扫描
go run ./cmd/modelcollide -v -write       # 重新生成 configs/model_collision.json（改了模型/清单后跑）
go run ./cmd/modelcollide -verify -strict # 重新读模型推导、逐字段对比、验收警告也算失败（需要模型）
go run ./cmd/modelcollide -check          # 校验游戏配置与生成文件一致（不需要模型，CI 可跑）
go run ./cmd/modelcollide -apply          # 同步手写配置：**默认 dry-run**，只打印该改什么
go run ./cmd/modelcollide -apply -yes     # 真的写进 configs/{resource_templates,buildings,creatures}.json
```

等价 make 目标：

| 目标 | 作用 |
|---|---|
| `make model-collide` | `-v -write` + `-check`（改了模型/清单后跑） |
| `make model-collide-verify` | `-verify -strict`（抓"改了模型忘了跑流水线"，CI 也跑这个） |
| `make model-apply` | `-apply`（dry-run；确认后手动加 `-yes`） |

资源根可以用 `GATE_ASSET_ROOT` 覆盖（CI 里把资源仓 checkout 到别处时用），
不改清单；`-asset-root` 优先级更高。

### 2.1 `-apply`：一个命令同步到服务端

- **只改清单 `targets` 声明的字段**，不新增字段、不做语义改名
  （`blocking` → `collision_radius` 这种迁移仍然留给人 + `configcheck` 报错）；
- **只做字节级就地替换**：其它字节一个都不动，所以 diff 里只剩变化的那个数字
  （仓库里 `creatures.json` 的 `"drops": [ { ... } ]` 是内联写法，一旦重新序列化整个文件都会变）；
- **默认 dry-run**。没人盯着的时候不该悄悄改配置。

### 2.2 自动验收（`-verify -strict` 会失败，`-check` 不涉及）

推导出来的形状会过四道自动检查——查的都是"肉眼看很难发现、错了却会静默错位"的性质：

| 检查 | 判据 | 不过会怎样 |
|---|---|---|
| **朝向** | `capsule_axis: body` 的模型，水平长轴必须是**局部 +Z** | **失败**。客户端把局部 +Z 对准朝向（`IsoCamera3D.FacingYaw`），长轴在 X 会让服务端碰撞胶囊与渲染差 90° |
| **贴合** | `body` 胶囊的取样带顶点落在胶囊外的比例 ≤ `max_outside`（默认 10%） | 警告。契约是"长宽刚好包住"，实测四足 2%~2.5% |
| **原点** | 非 `box` 形状：模型原点离地 \|minY\| ≤ 0.05 格 | 警告。圆/胶囊把原点当"格心 + 地面"，偏了竖直位置整体错 |
| **居中** | 形心到原点的水平偏差 ≤ `max_center_offset`（默认 0.10 格） | 警告。模型没居中应当重导出，而不是把半径算大 |

直立胶囊（人形）**不卡贴合度**：半径取的是躯干短边，手臂本来就在半径外
（实测玩家 87% 在圆柱外，这是设计意图）。

### 2.3 漏登记扫描

清单里的 `scan`（`filepath.Glob` 语法）命中的 `.glb`，凡没被 `models` 引用、又不在
`scan_ignore` 里的，会作为线索列出来——新加的动物/资源模型往往就是这种情况。
当前有 9 个未接入的动物模型（Alpaca/Bull/Cow/Donkey/Horse/Husky/Shiba Inu/Stag/White Horse），
接生物时直接用它们，不用再找美术。**这条只是线索，不会让流水线失败。**

## 2.4 渲染资源放哪

现在 `asset_root` 指向 `../starve-godot/GodotClient/assets`——服务端流水线依赖客户端仓库在本地旁边，
CI 上跑不了 `-verify`。推荐演进方向（尚未落地）：

1. **独立 `starve-assets` 仓库**（`models/` 用 git-lfs），客户端与服务端都作为依赖消费；
2. 服务端在清单里**钉住资源仓的 commit**，每条记录里已经写了 `model_sha256`（模型内容摘要），
   于是 `-verify` 能区分"模型内容变了"和"推导规则变了"；
3. CI 用 `GATE_ASSET_ROOT` 指到 checkout 出来的资源仓，跑 `-verify -strict`。

在资源仓落地之前，`-check`（不读模型）仍然是 CI 里的主力门禁。

## 3. 加一个模型要做什么

1. **把模型放进客户端资产**（`starve-godot/GodotClient/assets/models/...`），
   并在客户端代码里给它一个缩放常量（`ModelScale`）。
2. **在 `configs/models.json` 加一条**：

   ```json
   {
     "entity": "wood",
     "model": "models/ghibli-tree/ghibli_tree_godot.glb",
     "scale": 0.56,
     "scale_source": "GodotClient/Game/TreeActor3D.cs DefaultModelScale",
     "shape": "circle",
     "band": [0.0, 0.35],
     "percentile": 0.98,
     "targets": [{ "kind": "resource_template", "field": "collision_radius" }]
   }
   ```

   - `scale` **必须**等于客户端渲染该模型的缩放常量，否则算出来的格数和画面不一致
     （`scale_source` 里写清出处，方便对齐）；
   - `shape`：`circle`（树/岩，格心圆）| `capsule`（人物/动物，半径 + 身高）| `box`（建筑，占格盒）；
   - `band`：取样高度带（0..1），**树干只取下半段**、动物取躯干段（`0.25~0.75`）、
     建筑取全高；
   - `targets`：推导值必须落到哪个配置字段（`exact` 必须等于，`at_least` 必须 ≥，用于占格盒覆盖模型足迹）。
3. **没有 3D 模型的**（2D 精灵、程序化基本体、纯玩法尺寸）写 `fixed` 并**必须写原因**——
   让"这里为什么是手填的"留在数据里。
4. **跑 `make model-collide`**（重新推导 + 生成），再 `make model-apply` 看 dry-run 的 diff，
   确认后 `go run ./cmd/modelcollide -apply -yes` 落到手写配置，最后 `make model-collide-verify` 确认验收通过。

## 4. 简化规则（为什么不能直接取包围盒）

直接在包围盒上取半径/尺寸会错得离谱：

- 树/灌木的**树冠**比树干宽得多，可玩家应该能从树冠下面穿过去 → 只量树干（`band` 取下段）；
- 狼/鹿这类长条模型，**体长**（鼻子到尾巴）不是碰撞半径 → 半径取水平截面的**短边一半**；
- 角色张开的**手臂**、飘带、粒子片是视觉细节 → 用 `percentile` 裁掉两端离群点
  （0.98 = 两端各裁 1%；样本 < 100 时不裁，避免小样本把尺寸裁出可见误差）；
- 建筑要用**整格** → 足迹向上取整成 `box_tiles`。

推导出来的每条记录都带诊断字段：`points`（取样点数）、`extent_x/extent_z`（水平截面两条边，
用来核对是不是取错了轴）、`max_radius`（未裁剪的最远点）、`center_offset`（模型原点与取样段形心的偏差，
偏大说明模型没居中，应该让美术重新导出，而不是把半径算大）、`bounds`（模型包围盒，格）。

## 5. 新增字段落在哪

| 形状 | 落点 | 说明 |
|---|---|---|
| `circle` | `resource_templates.json: <kind>.collision_radius` | 服务端 `components.Block{Radius}`（占 1 格，可穿过但绕开更划算） |
| `box` | `buildings.json: <kind>.width/height` | 整格盒占位（`at_least`：配置不许比模型足迹小） |
| `capsule` | `creatures.json: <kind>.body_radius/body_height` | 生物简化碰撞体；配置缺这两项会 fail fast |

### 5.1 胶囊：长、宽、高怎么"刚好包住"

每条记录都带 `capsule`（也是调试渲染的形状）：

| 字段 | 含义 |
|---|---|
| `axis` | `vertical`（人物/树/建筑：段沿 Y）或 `body`（四足：段沿水平长轴） |
| `a` / `b` | 段端点（相对模型原点=服务端格心 + 地面，单位=格） |
| `radius` | 半径（按取样带量：树干/躯干，决定"被挡住时离多远"） |
| `height` | 模型总高（高刚好包住） |

规则：

- **宽**：半径按取样带的短边一半（树取树干、动物取躯干，手臂/鹿角不进半径）；
- **长**：四足的段从中心向两侧铺到 `max(|min|,|max|) - radius`，两端半球正好包住鼻子和尾巴
  （狼 ±1.06 + r 0.246 = ±1.306，模型 Z 范围 ±1.30 ✓）；
- **高**：`height` = 整个模型的 Y 跨度（不是取样带的高度）。

服务端移动直接用这套形状：`Moveable.body_radius` + `body_half_length`（四足）+ `facing`
（轴向 = 最近一次移动方向），碰撞层 `collision.World.SlideBody` 走"圆柱或胶囊"两种扫掠。
想更严格地包住肢体（比如把手也算进去）：把清单里的 `band` 调成全高 `[0,1]`、
`percentile` 调到 `1` —— 一行配置的事，改完 `make model-collide` 就能看到新半径。

`body_radius/body_height` 目前只作为契约数据落地（移动体半径还是全局常量
`systems.BodyRadius`）；接入"按实体半径移动"后 `MoveSystem` 直接读它。

## 7. 边界与后续

- **只支持 `.glb`**（二进制 glTF，自带 BIN chunk）；`.gltf` + 外部 `.bin` 请先导出成 `.glb`。
- **只取绑定姿势**（不做动画）：动物取静止姿态的躯干，够运动碰撞用；
  将来若某个动作会把身体撑得更宽（比如扑咬），在清单里给它更大的 `band` 或 `fixed`。
- **2D 精灵/骨骼动画**（lizard / spider / fishman）没法量：走 `fixed` 并写原因。
- **调试核对**：服务端 `GATE_DEBUG_COLLISION=1` 会把每个实体的 `DebugShape`（圆柱/盒/胶囊）
  随快照下发，客户端 `DebugShapeLayer3D` 画成半透明体——直接看"是不是刚好包住渲染模型"。
- **客户端预测**：玩家身体半径由服务端下发（`Moveable.body_radius`），客户端不要写死；
  四足胶囊目前只有服务端在用（客户端不预测生物移动），将来要让客户端预测生物时，
  `MovementSlide` 需要补同样的胶囊扫掠。
