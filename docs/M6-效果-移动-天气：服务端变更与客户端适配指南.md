# M6 效果 / 移动 / 天气：服务端变更与客户端适配指南

> 范围：M5-3（地形渲染）之后服务端新增的三块能力——效果系统、tick 制移动、天气系统。
> 本文档同时是**客户端适配清单**：客户端项目（start-client）按第 3 节逐项跟进。

## 1. 服务端变更摘要

### 1.1 效果系统（Effect，已完成验收）

**设计：行为=注册表。** 数据组件在 `internal/game/components`，行为（接口/注册表/具体效果）在 `internal/game/components/effect`，结算在 `systems.EffectSystem`（order 90）。

- 效果类型 = proto 枚举 `EffectOrder`：
  - `SPEED = 1`：速度修正，`param` 为百分比（正=加速，负=减速），加速/减速是同一个效果
  - `POISON = 2`：中毒，`param` = 每 tick 扣血量
  - `COLD = 3` / `HEAT = 4`：寒冷/炎热，由天气派生（温度阈值），`param` = 每 tick 伤害
- 强度走参数：`EffectInstance{ order, param }`，不再为每个强度写单独效果。
- 三类来源，统一进覆盖集（多源计数 + 参数求和，减到 0 才 Exit）：
  1. **地块效果**：`MapData.TileEffects/TileParams`（服务端内部，**不下发客户端**）；`configs/map.json` 的 `handplaced.effect_tiles`（`{effect, param, x, y}`）手摆，水→毒、雪→减速（-50）地形派生。
  2. **实体发射器**：`EffectEmitter` 组件（`repeated EffectInstance effects + radius`，半径 0 = 仅自身所在格），快照可见（植物/火堆等增益源）。
  3. **派生效果**：天气温度 → COLD/HEAT（`weather` 包注册的派生提供者）。
- 玩家身上挂 `Effects` 组件（快照可见）：`repeated EffectActive{ order, count, param }`。

### 1.2 tick 制移动（Moveable + MoveSystem）

- `Position` 仍是纯坐标（客户端契约不变，整格整数）。
- 新增 `Moveable{ interval, elapsed, queue[]MoveDir }` 组件（只挂玩家，快照可见）：`interval` 基础步进间隔（默认 2 = 每 2 tick 走一格，20Hz 下 10 格/秒），`queue` 是待执行方向命令队列。
- **`world.player.move`（`PlayerMove{dx,dy}`）语义改变**：
  - 非零 = 一次**方向步进**（每轴 -1/0/1，服务端 clamp），进队列按序消费，不立即移动；
  - `(0,0)` = **停止**，服务端清空队列；
  - 队列上限 32（防积压，满了丢弃新指令）。
- `MoveSystem`（order 95）每 tick 按 `interval` 消费队首一步；`SPEED` 效果按百分比修正间隔（+100% 减半、-50% 加倍、≤-100% 冻结）。

### 1.3 天气系统（Weather，本次新增）

- proto：`Season` 枚举（SPRING/SUMMER/AUTUMN/WINTER）；`WeatherState{ phase, season }` 挂在 **`Snapshot` 与 `SnapshotDelta`** 上（像 DayCycle 一样每 tick 下发，随存档保存/恢复）。
- 服务端采样模型（纯函数、确定性，seed = 地图种子）：
  `WeatherQuery{ X, Y, Height, TileType, Season, Tick }` → `WeatherSample{ Temperature, Fog, Rain, WindDirX/Y, WindSpeed, Light }`。
- 局部修正：`Fan{strength, dir_x, dir_y, radius}`（风力 + 下风向降雾）、`HeatSource{strength, radius}`（升温 + 降雾），实体组件。
- 配置：`configs/weather.json`（`year_ticks`、`cold_at/cold_damage`、`heat_at/heat_damage`）。
- 玩法挂钩：温度 ≤ `cold_at` → 寒冷效果，≥ `heat_at` → 炎热效果（走效果系统，扣血在服务端）。

### 1.4 生物系统（Creature，本次新增）

- `CreatureKind` 枚举（RABBIT/WOLF）；`Creature` 组件携带行为状态 + 从模板拷贝的静态属性
  （身份/仇恨表/游荡/掉落），快照与存档自包含。
- **AI 状态机（`AISystem`，order 92，效果后、移动前）**：四态 `idle/chase/attack/flee`，
  每 tick 用当前输入快照评估转移（AOI.Visible + LastHitBy + HP + 距离），不是事件驱动：
  - 目标候选 = **AOI.Visible**（+ 最近受击者），不全局扫描实体；
    敌对关系配置化：玩家看 `hostile_players`（false = 友好生物），生物看 `hostile`
    （如狼猎兔子）；仇恨更新（感知加基础仇恨、受击加高仇恨、每 tick 衰减、超 leash 放弃）；
  - 无目标 → idle（游荡）；有目标：攻击范围内 → attack，范围外 → chase；HP ≤ FleeHP → flee。
- **受击标记**：`AI.LastHitBy/LastHitAt`（tick 窗口，默认 `hit_memory_ticks`）——"攻击是一瞬间，
  被攻击者需要被告知"用字段 + 窗口表达，过期即失效，无需主动清空；统一攻击结算
  `systems.ApplyAttack`（玩家命令 / 生物 AI 共用）：扣血 + LastHitBy + 仇恨 + 受击打断。
- `Weapon` 组件（攻击范围/伤害/冷却）：从 Creature 拆出，生物生成时从模板挂，玩家装备后续复用。
- **寻路**：`worldmap.FindPath` 确定性 BFS（非水可走），路径写入 `Moveable.Queue` 由
  `MoveSystem` 消费；逃跑 `worldmap.FleeDir`（远离威胁点 + 可走校验）。有地图不可达时不贪心下水。
- 死亡掉落：生物死亡挂 Dead → 按组件掉落表生成 Loot（移除 Creature），拾取复用现有流程。
- 配置：`configs/creatures.json`（模板）+ `map.json handplaced.creatures` 手摆出生。
- **AOI 感知（order 91，先于生物决策）**：每生物挂 `AOI{radius, visible}` 组件；两轮算法——
  第一轮按方形 radius 标记覆盖方块（全局网格缓存），第二轮把范围内 liveable 写入覆盖者的
  `visible`；复杂度 ≈ N·r² + M·C，与地图大小无关（touched 列表，无整表清零）。
  **降频**：默认每 4 tick（4Hz）刷新一次，`GATE_AOI_INTERVAL` 可调；`visible` 是派生数据
  （确定性排序）；`GATE_DEBUG_AOI=true` 时 visible 进快照并随变更推送，方便端上调试感知范围。
- **天气帧下发**：服务端按间隔（默认每 20 tick = 1Hz，20Hz 下）推送 `WeatherFrame`（route `world.weather.frame`）：
  粗粒度网格（cell_size=10，80×80 → 8×8 单元），每个单元带 `fog/rain/temperature`，外加全局
  `wind_dir_x/y` + `wind_speed`——客户端据此渲染雾层、雨粒子与风向漂移。间隔可配
  `WorldConfig.WeatherFrameTicks`（负值关闭）。

## 2. proto 变更清单（客户端需同步）

同步服务端最新 `pkg/proto/game/game.proto` + `pkg/proto/message.proto` 到 start-client 的 `proto/`，然后跑 `buf generate`。

**新增类型：**

| 类型 | 说明 |
| --- | --- |
| `Moveable` / `MoveDir` | 移动状态（interval/elapsed/queue）与一步方向 |
| `EffectInstance` | 效果实例（order + param） |
| `EffectActive` / `Effects` | 玩家生效效果（order + count + param） |
| `EffectEmitter` | 实体效果发射器（repeated EffectInstance + radius） |
| `Fan` / `HeatSource` | 风扇 / 热源（局部天气修正，可选渲染） |
| `Season` / `WeatherState` | 季节枚举；天气状态（phase/season） |
| `WeatherFrame` / `WeatherCell` | 天气帧（周期推送）：雾/雨/温度网格 + 全局风 |
| `CreatureKind` / `Creature` / `ThreatEntry` | 生物类型枚举；身份+仇恨表；仇恨表条目 |
| `AI` / `Weapon` | 行为状态机（state/target/flee/受击标记）；攻击能力（范围/伤害/冷却） |
| `AOI` | 感知组件（radius + visible，debug 模式 visible 才下发） |

**变更：**

- `EffectOrder` 枚举值：`SPEED=1`、`POISON=2`、`COLD=3`、`HEAT=4`（原来的 SPEED_UP/SLOW_DOWN 已删除）。
- `Snapshot` 增加 `weather` 字段（全量）；`SnapshotDelta` 增加 `weather` 字段（增量，每 tick 携带）。
- 推送路由新增 `world.weather.frame`（服务端 → 客户端）。
- 组件名 `"Moveable"`（上一版草案叫 Mover，未发布，直接按 Moveable 适配）。

注意：protobuf-es 会去掉枚举前缀，生成代码里是 `EffectOrder.SPEED`、`Season.SUMMER`（不是 `EFFECT_ORDER_SPEED`）。

## 3. 客户端适配清单

### 3.1 proto 同步（必做）

1. 覆盖 `start-client/proto/game.proto`、`proto/message.proto` 为服务端最新版本；
2. `buf generate` 重新生成 `src/core/generated/*`；
3. 编译修正受影响的引用（旧 EffectOrder 枚举名、Snapshot 结构新增字段）。

### 3.2 移动协议（必做，影响手感）

- **输入层**：键盘/摇杆按住时按固定节流发送 `PlayerMove{dx,dy}`（建议 ≤ 50ms/次，即不高于 tick 频率）；**松开立即发 `{0,0}`** 停止。
- **渲染层**：位置仍按服务端 `Position` 增量做插值（现有逻辑不动）；`Moveable` 组件可用来做走路动画节奏（可选，先用 interval 近似）。
- 旧客户端"按一次发一步"仍能被服务端接受（进队列），但会排队、手感滞后，必须尽快改成"按住 + 停止"。

### 3.3 效果 / buff 渲染（建议做）

- 解析玩家快照里的 `"Effects"` 组件 → 显示 buff/debuff 图标（`order` + `count` + `param`，如 COLD/POISON 图标可显示强度）。
- 可选：解析 `"EffectEmitter"` 实体 → 绘制光环范围（radius）；`"Fan"`/`"HeatSource"` → 风扇/火堆特效。
- 扣血结算在服务端，客户端只展示状态。

### 3.4 天气（季节 + 雾/雨渲染）

- 每 tick 增量快照读 `weather.season` → 季节 UI / 整体色调（如冬季偏冷色）。
- 订阅 `world.weather.frame` 推送，解析 `WeatherFrame`：
  - `cells`（行优先，`cells_per_row` × 总行数，覆盖全图）→ 每单元 `fog`（雾层透明度）、`rain`（雨粒子密度/速度）、`temperature`（可选色调/结冰）；
  - 全局 `wind_dir_x/y` + `wind_speed` → 雨粒子漂移方向、旗帜/草摆动；
  - `cell_size` = 每单元覆盖的世界格数（客户端换算像素坐标，建议做双线性插值让雾/雨平滑过渡）。
- 渲染建议：雾用整屏半透明层按单元做渐变；雨用粒子系统按 `rain` 值控制发射率，粒子速度叠加风向。

### 3.6 生物渲染（建议做）

- 快照新增 `"Creature"`（kind/仇恨）、`"AI"`（state/target/flee）、`"Weapon"` 组件，血量走
  `Health` → 按 kind 渲染生物（兔子/狼），可选血条、状态提示（追击/逃跑）；
- 攻击/拾取复用现有命令，客户端无需新增协议；
- 注意：目前客户端对未知实体可能不渲染，需要给带 `Creature` 的实体加默认表现，否则看不到生物。

> **已知问题（客户端已确认）**：雨粒子当前是**屏幕空间**实现的（`scene.ts` `spawnParticle` 在
> 屏幕坐标生成、掉出视口后按屏幕范围重新撒回），只在绘制时用 `screenToWorld` 查雨量过滤。
> 表现：镜头跟随玩家移动时，雨整体跟着屏幕飘（像"以玩家为中心"），而雾是**世界锚定**的所以不飘。
> **修复**：把雨粒子改成世界空间，与雾一致——
> ① 在世界坐标生成粒子（建议落在雨量 > 阈值的格子内）；
> ② 每帧更新**世界坐标**（下落/漂移速度按 `camera.scale` 换算）；
> ③ 绘制统一走 `camera.worldToScreen`；掉出雨区/地图再回收。
> 改完后镜头平移时是"相机在静止雨幕上移动"，不再跟手。

### 3.5 无需改动的部分

- 路由表：没有新增 pomelo 路由，天气状态随 SnapshotDelta 自动下发。
- `MapConfig`（地形高度/类型契约）：不变。
- **区域/生物群系为服务端内部**：`BiomeType` 枚举虽在 proto 里，但没有任何客户端消息引用；
  `tile_regions`/`region_weather` 只在存档里。区域只是改变了 `corner_types` 的内容分布
  （仍是 Water/Sand/Grass/Rock/Snow 五种类型，无新增），客户端渲染逻辑不需要改动。

## 6. 性能压测记录：AOI 感知

> 环境：Apple M4 Pro；`go test -bench BenchmarkAOISystem -benchmem -run '^$' ./internal/game/world/`
> （500~2000 次迭代，数值有噪声，量级可信）。

**复杂度**：`O(N·r² + M·C)`（N=感知者，M=liveable，C=单格覆盖数）。
与地图大小无关——用 touched 列表只清"本轮被标记过的格子"，不再整表清零
（1024² 空图：0.5ms → 0.8µs）。

**每 tick 全量（降频前）**：

| 场景 | 单次耗时 | 占 20Hz tick |
| --- | --- | --- |
| 30 生物 / 80² | ~16 µs | ~0% |
| 100 生物 / 80² | ~70-107 µs | ~0.2% |
| 200 生物 / 80² | ~330-580 µs | ~1% |
| 5000 生物 / 512² | ~5.0 ms | 10% |
| 5000 生物 / 1024² | ~4.8 ms | 10% |
| 10000 生物 / 1024² | ~18 ms | 36% |
| 10000 生物 / 2048² | ~20 ms | 40% |

**每 4 tick 刷新（降频后，`GATE_AOI_INTERVAL=4` 默认）**：

| 场景 | 单次耗时 | 占 20Hz tick |
| --- | --- | --- |
| 5000 生物 / 512² | ~1.2 ms | 2.4% |
| 5000 生物 / 1024² | ~1.2 ms | 2.4% |
| 10000 生物 / 1024² | ~3.8 ms | 7.6% |
| 10000 生物 / 2048² | ~4.5 ms | 8.9% |

**结论**：

- 地图大小已不是瓶颈（同只数下 512²/1024²/2048² 几乎无差别）；
- 瓶颈是 N·r² 标记本身，且密度上来后**超线性**（5000→10000 只，耗时 ×3.6~4，
  因每格覆盖数 C 变大 + 随机 append 的缓存压力）；
- 5000 只每 tick 全量可撑 20Hz（10%）；10000 只需降频（4Hz 后 8%）；
- 降频代价 = 感知最多滞后一个刷新周期（4 tick = 200ms @20Hz），对仇恨/移动几乎无感；
- 若生物量继续上涨：感知频率再降、或做增量（仅移动实体重标出入格子）、或按需 A* 预计算。

**生物 AI 规模压测（5000 只，AOI+AI+移动管线，Apple M4 Pro）**：

| 场景 | 单 tick 耗时 | 分配 |
| --- | --- | --- |
| 2500 狼 + 2500 兔 / 256²（密集） | ~7.9 ms | 4.8MB / 3535 alloc |
| 2500 狼 + 2500 兔 / 512²（稀疏） | ~3.7 ms | 5.4MB / 3888 alloc |

- 完整世界 tick（20 轮 × 2 次）平均 ~5ms/tick：确定性一致、追捕/攻击/逃跑行为正常、无负血；
- 5000 只占 20Hz tick 的 8~16%，**可跑但偏紧**；瓶颈是分配（~5MB/tick，主要来自
  `FindPath` 每次新建 parent 数组 + AOI/移动零碎分配），AI 决策本身很便宜；
- 优化方向：FindPath 复用 parent 缓冲、路径按"目标移动超阈值"重算降频。

**寻路算法选型（BFS vs A* 对比，Apple M4 Pro）**：

| 场景 | BFS | A*（goal-biased） |
| --- | --- | --- |
| 512² 短路径 | 117µs / 1.0MB | **8.8µs / 16KB** |
| 512² 对角 | 1.8ms / 5.6MB | **455µs / 662KB** |
| 2048² 短路径 | 1.5ms / 16.8MB | **9µs / 16KB** |
| 2048² 对角 | 30ms / 122MB | **2.1ms / 3MB** |

- 结论：**全面采用 A\***（曼哈顿启发式 + goal-biased tie-break：f 相同优先更深，空旷地形拉直
  冲向目标，避免整矩形展开；稀疏 visited map，分配 O(路径长度)）。BFS 的固定 O(WH) parent
  分配在短路径/大图上反而更贵；混合方案（短→BFS）继承该开销，已废弃。
- 5000 只规模下三者几乎无差别（实际都是短路径、调用频率低），路径算法非规模瓶颈。
- **地图单数据源**：`MapData` 是唯一地图（静态地形即时推导可走性 + 动态阻挡层 `Blocked`），
  建筑等 `Block` 组件实现 ECS 生命周期钩子（`OnAdd`/`OnRemove`），挂载/销毁时由 ECS 内核
  自动增量更新阻挡层，AI 追击/逃跑/玩家移动直接读 `MapData.Walkable`；启动与存档恢复时全量重建一次。
