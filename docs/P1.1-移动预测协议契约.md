# P1.1 移动预测协议契约

## 目标

锁定服务端权威移动与客户端预测之间的最小稳定契约，覆盖重连、重复/迟到输入、
服务端 tick、输入确认和两端碰撞公式一致性。P1.1 不把伤害、采集或制作结果交给客户端。

## 协议

- 握手声明 `protocol_version=1.1`，能力包含 `input_epoch_ack`、`snapshot_tick`、
  `effective_move_speed`。
- 登录成功后服务端分配非零 `input_epoch`。同 UID 重连会获得新 epoch，旧连接被踢。
- `PlayerMove` 携带 `(input_epoch, seq)`；seq 在单个 epoch 内从 1 单调递增。
- `Snapshot` / `SnapshotDelta` 携带 `(tick, input_epoch, last_accepted_seq)`。
- `Moveable.effective_speed` 是地块/状态效果修正后的权威速度；客户端预测不得使用基础
  `speed` 替代，否则雪地减速会持续产生回拉。几何坡度不写入该字段：两端在步进里再乘同一套
  投影边长比（`testdata/slope_speed_golden.json`），高度场用崖壁带采样。
- ACK 只在移动命令通过世代、顺序、实体所有权和位置组件校验后推进。
- 同 epoch 下 `seq <= last_accepted_seq` 的重复或迟到输入丢弃；不同 epoch 的输入丢弃。
- 服务端仍临时接受 `(epoch=0, seq=0)` 的旧客户端移动，但它不参与 ACK。
- 阻挡分三层，两层要进预测（地形 + 形状）、一层只影响服务端寻路（占位代价）：
  - **地形层**：`MapData.Walkable` 只看水/悬崖，跨格不可走就贴边停在边界外侧（硬墙）；
  - **形状层**：`Block` 组件给出形状——`radius > 0` 是格心圆柱（树/岩，占 1 格），
    `radius == 0` 是 `width × height` 的占格盒（建筑/工作站）。移动是连续扫掠 +
    沿接触切面滑动，所以能贴着树干/墙面走；半径也随 `TemplateConfig.collision_radius` 下发。
  - **占位层**（服务端寻路用）：占位格仍然可走，只加寻路代价（圆 6 / 盒 1000）并作为
    放置冲突依据——占位不是硬墙。
- **实体碰撞体（形状的第二种来源）**：`Moveable` 下发 `body_radius` / `body_height` /
  `body_half_length` / `facing_x,y`——由客户端模型推导（`configs/models.json` +
  `make model-collide`）。圆柱（人物/树：`body_half_length = 0`）与胶囊（四足：段沿朝向铺开，
  长宽刚好包住模型）两种。客户端预测**必须用服务端下发的 `body_radius`**
  （`OwnMovementSim.SetBodyRadius`），不要写死常量；缺省值 `systems.BodyRadius = 0.305`。
  四足胶囊目前只有服务端在用（客户端不预测生物的移动），将来客户端要预测生物时，
  `MovementSlide` 需要补同样的胶囊扫掠。
- **调试**：`GATE_DEBUG_COLLISION=1` 时每个实体的简化碰撞体以 `DebugShape` 组件随快照下发
  （圆柱/盒/胶囊，模型局部空间），客户端渲染出来核对形状；这不是玩法数据，关掉就消失。

移动体半径缺省值由服务端常量 `systems.BodyRadius` 给出（当前 0.305 格 = 玩家模型躯干），
按实体的值走 `Moveable.body_radius`——两者都属于本契约。

`tick` 是世界固定步长计数，不是墙钟时间。`last_accepted_seq` 只代表服务端接受了该方向
意图，不代表客户端预测位置正确，位置仍以快照为准。

## 客户端预测

移动命令表达“持续方向”，不是逐帧位移。因此客户端不重放一长串历史位移：

1. `OwnMovementSim` 按当前本地意图和服务端相同的 `effective_speed × 坡度因子 × dt`、对角归一化推进；
2. 推进量先过**形状层**：对半径 `BodyRadius` 的圆做扫掠（连续，不穿树），命中就把剩余位移
   投影到接触切面继续滑（`skin = 1e-3` 回退，最多 4 次接触）；再按**格子层**的
   `stepAxis` 提交到锚点/子格，目标格不可走则贴墙停在边界；
   （服务端 `systems.MoveBody` = `collision.World.Slide` + `stepAxis`，算法要点见
   [`占位物与墙角滑动-Godot客户端适配指南`](占位物与墙角滑动-Godot客户端适配指南.md)）
3. 收到权威位置时按误差软校正/硬跳，当前本地意图保持；
4. 旧 epoch 或倒退 tick 的增量帧不应用；
5. 未确认移动超过 4 条时暂停继续预测，防止断网时无限领先；ACK 追上后恢复。

服务端与客户端共享 `testdata/movement_golden.json` 与 `testdata/slope_speed_golden.json`。客户端质量门禁同时检查文件同步，
Go/C# 测试分别执行同一组负方向、对角归一化、贴墙、沿墙滑动和坡度因子向量。
`movement_golden.json` 里的形状层向量额外带 `shapes`（`{kind:"circle",x,y,r}` 或
`{kind:"box",x,y,w,h}`）、`body_radius` 与可选的 `tol`（接触回退 `skin` 带来的容差）；
`blocked` 表示硬墙格（地形水/悬崖）。

## 边界

- 阻挡预测只覆盖客户端已知的静态信息：占位物（树/岩/建筑）都随快照到达，
  两端用同一套公式预测；服务端若新增客户端不知道的碰撞体，位置仍以快照为准。
- 攻击、制作、采集只预测动画/进度展示，不预测权威结果。
- WebSocket 本身有序可靠；重复、旧世代、倒退 tick 测试用于覆盖重连与应用层重试，
  不是模拟 UDP。

## 验收

服务端：

```bash
make check
```

客户端：

```bash
make check
STARVE_GATE_URL=ws://127.0.0.1:8081/ws make e2e
```

`ProtocolSmoke` 会验证握手能力、全量快照 epoch、移动后 ACK 追平和停止确认。
