# P1.4 跨端一致性语料（移动/碰撞/ORCA）

> 上游：`P1.1-移动预测协议契约.md`、`P1.7-序号锚定-命令流-追赶-渲染.md`（客户端侧）、
> `docs/P1.3-输入流-序号消费与多步追赶.md`。
>
> 一句话：**把"两端实现是否一致"从口头约定变成 CI 里可判定的红/绿。**

---

## 1. 为什么这能保证两端一致

1. **两端跑的是同一个确定性纯函数**：`下一状态 = step(状态, 操作, dt, 世界输入)`。
   不依赖时钟、随机数、外部 IO ⇒ "一致"本质是**函数相等**，而不是"看起来差不多"。
2. **语料把它变成可判定的事实**：一组固定的「场景输入 → 期望位移」，两端各自跑自己的实现去比。
   任何分歧（运算顺序、`float`/`float64`、`0.999` 边界钳制、多接触先解谁、ORCA 退化与并列打破）
   都会在 CI 里当红，而不是等玩家走两步感觉卡。
3. **期望值由权威侧生成**：生成器直接调**服务端真实求解路径**（`MoveSystem` + 生产同款 solver），
   不是另写一套公式 ⇒ 语料本身即 ground truth，客户端是被校验方，
   "接近但不相等"这种会持续制造校正的漂移无法潜伏。
4. **值钱的是边界覆盖，不是均匀随机**：数学主体好对齐，分歧都藏在**分支交界**。
   所以采样刻意偏向：贴墙 `0.999/0.001`、恰好接触、对角线归一化、坡度因子钳制、
   多接触滑动、ORCA 迎面/追尾/三体。
5. **两道护栏**：① 两仓语料**逐字节一致**（`scripts/check_move_corpus_sync.py`，已挂进 `make contract-check`）；
   ② 容差与浮点约定写死在这里（见 §4），不靠放宽容差"变绿"。

## 2. 语料

* 文件：两仓 `testdata/move_corpus.jsonl`（**必须逐字节一致**）。
* 规模：**360 条**（9 类 × 40），`seed=11`，`sha256` 前缀 `fefbafdc04466eaa`。
* 格式：JSONL，**首行是元信息** `{"meta":{"seed":11,"count":360}}`（回放测试必须跳过），其余每行一个场景：

```json
{"name":"base_000","category":"base","start_x":14.52,"start_y":12.54,"dx":1,"dy":0,
 "speed":11.39,"dt_ms":50,"body_radius":0.3,"want_x":15.09,"want_y":12.54}
```

| 字段 | 说明 |
| --- | --- |
| `blocked` | 硬墙格（地形水）：与 `MapData.CornerTypes` 同一套"左上角角地形"判据 |
| `heights` | 线性高度场 `h(x,y)=base+grad_x·x+grad_y·y`。**硬性约束：整张地图的角点高度必须是 [0,255] 内的整数**——服务端把它存进 `CornerHeights []byte`，越界会按低 8 位回绕（-1→255…），那时"真实求解的高度场"≠"JSON 声明的场"，任何客户端都复现不了（§5.4）。生成器用 `newRamp` 按梯度跨度自动取 `base`（`span=(|gx|+|gy|)·24`，`base=span+16` ⇒ 高度 ∈ [16,208]），`step()` 里 `assertHeightFieldFits` 兜底硬校验 |
| `shapes` | `circle{x,y,r}`（中心） / `box{x,y,w,h}`（左上角锚点）。**没有 capsule**（见 §5.2） |
| `body_radius` | 被求解移动体半径（客户端必须 `SetBodyRadius` 同一个值） |
| `neighbors` | ORCA 邻居（动态胶囊）：`{x,y,vx,vy,radius,half_length,max_speed}` |
| `want_x/want_y` | 期望位移（服务端真实路径产出，一个 tick） |

九类场景各 40 条：`base`（四方向 + 16/33/50ms）、`diagonal`（对角归一化）、
`slope`（上下/侧坡，梯度 ±1/±2）、`wall`（贴边停 0.999/0.001、跨界被挡、贴墙滑动）、
`circle`（正撞/擦过/恰好相切）、`box`（正面停/沿面滑/角点擦过）、
`capsule`（**静止的移动体**：正前/侧擦/斜穿）、`orca`（迎面/追尾/并排/三体，**刻意带 0.05~0.1 横向偏移**）、
`combo`（坡 + 形状 + 邻居同时出现）。

## 3. 怎么跑（本地与 CI 同一入口）

```bash
# 本地（两仓是兄弟目录，零参数）
python3 starve-godot/scripts/corpus_align.py
make -C starve-godot corpus-align                       # 同一条命令的 make 封装

# 显式选路径（本地任意位置）
python3 starve-godot/scripts/corpus_align.py --server-dir ~/work/starve --client-dir ~/work/starve-godot

# 改过移动数学/碰撞/ORCA/坡度之后：重新生成（权威侧生成 → 自动复制到客户端）
python3 starve-godot/scripts/corpus_align.py --regen --seed 11 --count 360

# CI（服务端 checkout 在 .contract-server）
STARVE_SERVER_DIR=.contract-server make corpus-align
```

运行器依次做四件事（每步 `PASS/FAIL` + 耗时 + 细节，任一步失败非零退出）：
环境检查 → **两仓语料逐字节一致** → 服务端回放（`go test -run TestMoveCorpusVectors ./cmd/movecorpus/`）
→ 客户端回放（`dotnet test --filter MovementCorpusTests`）。

还有一个**本地图形工具**（选路径、点一下就跑，纯标准库、跨平台）：见
`starve-godot/scripts/README-corpus-align.md`。

## 4. 容差与浮点约定

| 侧 | 判据 | 理由 |
| --- | --- | --- |
| 服务端回放 | **精确相等（容差 0）** | 生成与回放是同一份代码、同一台机器，运算顺序完全一致，本来就该逐位相同；给容差会把"悄悄改了运算顺序"放过去 |
| 客户端回放（声明场） | **1e-5** | 跨语言/跨精度：客户端状态是 `float`(32 位) 而服务端是 `float64`，中间量精度不同。1e-5 格 = 0.00001 格，远小于一个 tick 的位移（0.25~0.75 格），不会掩盖真问题 |
| 客户端回放（生产采样） | **1e-5** | 同一条语料再按**生产采样路径**回放一遍：把声明场落成 byte 角点网格 → `TileMap.LogicalHeightAt`（= `SlopeMesh.SampleHeight`，含 `|Δh|≥1` 的崖壁带）⇒ 同时校验两端**采样实现**（`worldmap.HeightAt` vs `SlopeMesh`）本身一致，而不只是"客户端数学 == 服务端 want" |

**坡度这一类的关键事实**（别被"线性场"误导）：移动/坡度用的高度**不是双线性**，
而是崖壁带采样（`EdgeHeight`：`|Δh|≥1` 时把落差压进 `CliffBand=0.22`）；
`TileMap.HeightAt` 只在 `SmoothSlopes` 时才是双线性，**不能拿去算坡度**。
线性场下崖壁带对"坡度因子"是平移等变的（所以解析式也能对上），
但真实生产接线两端都必须走崖壁带采样（客户端 `GameRoot`：`_ownSim.HeightAt = _tilemap.LogicalHeightAt`）。

生成器与回放测试**同包**（`cmd/movecorpus/`）：这样"期望值"与"回放"共用同一条真实求解路径，
不会出现"生成用 A、校验用 B"的假绿。

## 5. 已知不覆盖 / 待修的一致性差异

### 5.1 ORCA 对称打破：两端开关不同（**待修**）
* 服务端生产 solver：`NewDefaultMoveSolver()` → `NewORCASolver(...)`，`breakSymmetry = **false**`。
* 客户端 `OwnMovePredictor`：`new OrcaAvoidance(OrcaOptions.Default, **true**, entityId)`。
* 后果：**完全共线**的正面对撞，两边会选不同侧（甚至一边停死）⇒ 预测与权威不一致 ⇒ 反复校正。
* 现状：语料的 `orca` 类**刻意带横向偏移**避开退化点，所以现在两端能对上；
  修法是把服务端也按实体 id 做对称打破（`NewORCASolverFor`，key = 实体 id），改完再补"完全对称正面对撞"场景。

### 5.2 胶囊：客户端滑动会当硬障碍，服务端只走 ORCA
* 服务端静态碰撞索引只有 `circle/box`；胶囊只作为**动态体**存在，动态体之间走 ORCA 软避让。
* 客户端的 `MovementSlide` 若被喂进胶囊，会把它当**硬障碍**（且不看 `Owner`，曾经因此"本地预测撞自己"）。
* 因此：**生产接线里客户端只喂静态形状**；语料同样不喂静态胶囊，
  `capsule` 类用"零速度邻居"表达静止移动体。

### 5.3 其它不覆盖
ECS 接线（AOI 裁剪、dirty 通道、命令队列）、真实地形高度场（语料用线性坡 + 崖壁带采样）、
多 tick 连跑与状态累积、离散操作（攻击/投掷/使用）。

### 5.4 已修：角点高度越界回绕（曾让 `slope_004`/`slope_015` 必红）
* 症状：客户端回放 **358/360**，`slope_004`（`8-1x+0y`）差 0.0587 格、`slope_015`（`8+2x-2y`）差 0.3297 格，
  量级是"真分叉"而不是浮点噪声；其余 8 类 40/40 全绿。
* 根因**在生成器、不在客户端数学**：生成器用 `base=8` 配 `grad∈{±1,±2}`、角点 `0..24`，
  角点高度必然出现负值；而服务端把它写进 `CornerHeights []byte`，Go 的 `byte(负值)` 取低 8 位
  **回绕**（-1→255、-2→254…）⇒ 服务端真实求解的高度场与 JSON 里声明的线性场不是同一个东西，
  JSON 的 `heights` 字段也**无法表达**回绕后的场，于是任何客户端拿声明值都复现不了。
  （用回绕模型复刻 40 条 slope，与服务端 `want` 吻合到 1e-9；解析模型只差这 2 条 ⇒ 证据闭环。）
* 修法：① 生成器改 `newRamp`（`base` 由梯度跨度自动抬到值域内，±2 双轴跨度 96 ⇒ `base=112`，高度 ∈ [16,208]）；
  ② `step()` 加 `assertHeightFieldFits` 硬校验（越界直接 panic，不再静默生成废语料）；
  ③ 客户端回放同步加 `AssertHeightFieldInDomain`，并新增第二遍"生产采样路径"回放。
* **教训（写进契约）**：语料必须落在**真实定义域**内；一旦某个字段无法表达实现真正用的值，
  这份语料就已经失效——正确反应是修生成器，**不是放宽容差**（容差只用来吸收 float32/float64 表示差）。

## 6. 什么时候必须重新生成语料

改到下面任何一项，都要 `--regen` 并**人工确认差异可解释**（不许直接照单全收）：

* `internal/game/systems/move_solver.go`（滑动/力/ORCA 参数）、`move_system.go`（步进/钳制）
* `internal/game/worldmap/slope.go`（坡度因子）与任何影响 `Walkable` 的改动
* 客户端 `Starve.Core/MovementSlide.cs`、`OwnMovePredictor.cs`、`SlopeSpeed.cs`、`OrcaAvoidance.cs`、`SlopeMesh.cs`
* 语料生成器本身（新增场景类别/字段，或改 `worldSize`/`newRamp`）
* **不变式（改了必须让 CI 拦下，不能只靠人记）**：`heights` 的角点值必须是 [0,255] 整数（§5.4）；
  `blocked` 只能表达"左上角格不可走"；`shapes` 的坐标是中心/左上角锚点，**不许再套 +0.5 格转换**。

改完客户端实现之后**必须重新生成**吗？不必：客户端的职责是"跟上"权威，
所以流程是**服务端改动 → 重新生成 → 客户端回放红 → 修客户端直到绿**。
只有服务端数学变化才需要重新生成。
